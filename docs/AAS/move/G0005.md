## 1. Introduction（SCAIとは何か）

**SCAI（Structured Cooperative AI Framework／正式呼称：スカイ）** は、
人間とAIが対等に協働できるよう、**構造化文書と階層体系**を基盤とした総合フレームワークである。

SCAI は、単なるテンプレート群ではなく：

* 思想（G0000）
* 原則（G0100）
* 抽象規範（G0200）
* 全体地図（G0300）
* 番号体系（G0400）
  といった **体系としての背骨** を持つ。

本書 G0005 は **SCAI を初めて読む人のための公式入口文書** であり、
SCAI 全体像を最短で理解するために設計されている。

---

## 2. Why SCAI?（目的とメリット）

### Before（従来の問題）

* 文書・仕様・チェックリストが乱立
* フォーマットに統一がなく、属人化
* AI が誤読しやすい文書構造
* チーム間で品質基準がバラバラ

### After（SCAI 導入後）

* A/B/C/D の階層構造に統一
* 構造化 Artifact により誤読が激減
* B層により分野構造が標準化
* C層手法により実務工程が安定
* 番号体系による参照一貫性

### Benefit Summary

* **AI と人間の誤解が減る**
* **成果物が一貫し、構造が崩れない**
* **自動生成・検証・変換が容易**
* **組織全体の文書品質が安定**

## 3. SCAI の基本哲学

> **注記:** SCAI の原則（G0100）は背景思想（G0000）に基づき定義されている。

### 3.1 Structure-First

文章ではなく **構造（Structure）** が意味を決定する。

### 3.2 Cooperative Intelligence（協働AI）

AIは人間の代替ではなく、**対等かつ補完的パートナー**。

### 3.3 One-Way Layer Architecture

A→B→C→D の **一方向構造** により、品質と一貫性を保証する。

### 3.4 Artifact モデル（概要）

> **注記:** identifier や sectionId などの詳細定義は Appendix B（Glossary）を参照。

* Metadata Layer
* Structure Layer（意味の主役）
* Content Layer（補助）

            │

## Appendix E – Before/After 比較

### **E1. 導入前（Before）に起きがちな問題**

* 文書が属人的で構造が統一されていない
* AI が誤読し、期待通りに生成されない
* チェックリスト・仕様書・メモなどの形式がバラバラ
* プロジェクトごとに品質が大きくぶれる
* 文書更新の履歴が追跡困難

### **E2. 導入後（After）の改善**

* A/B/C/D の階層により責務が明確化
* 構造化 Artifact により誤読が激減
* B層による文書構造の標準化
* C層手法により実務工程が安定
* G/P 番号体系により参照性が向上

### **E3. Before/After 一覧表**

| 項目     | Before（従来） | After（SCAI導入後） |
| ------ | ---------- | -------------- |
| 文書構造   | 人ごとにバラバラ   | A/B/C/D の構造に統一 |
| AIとの協働 | 誤読が多い      | 構造化され誤読が激減     |
| 標準化    | なし         | B層による分野標準化     |
| 手法     | 属人的        | C層でテンプレ化       |
| プロジェクト | 標準と混在      | Pxxxx で独立      |
| 追跡性    | 不明瞭        | 番号体系により明瞭      |

## Appendix F – Artifact 構造詳細例

### **F1. YAML形式の Artifact 例**

```yaml
identifier: G0203

  - ref: G0200
    type: derives

  - sectionId: 1
    title: Purpose
  - sectionId: 2
    title: Rules

      - ruleId: 2-1
        title: Structure Determines Meaning
      - ruleId: 2-2
        title: No Ambiguity
content:
  Purpose: >
    この文書は SCAI の構造原則に従って作られる…
  Rules:
    2-1: >
      構造が意味を決定することを示す。
    2-2: >
      暗黙的・曖昧な記述を禁止する。
```

### **F2. ポイント**

* structure が意味の主役
* content は従属
* relations が根拠を明示
* identifier が位置づけを保証

## Appendix G – Anti-Patterns（誤用例）

### **G1. C層 → A層 の直接参照**

```
❌ G0304 が G0100 を直接参照
```

理由：階層逆流（A→B→C→D）を破壊する。

---

### **G2. 分野IDの勝手な変更**

```
❌ G0300（分野03）を分野08へ変更
```

理由：分野IDは「意味そのもの」。恣意的変更は構造を破壊する。

---

### **G3. 構造無視の自由記述文書**

```
❌ structure が存在しない
❌ sectionId / ruleId が無い
```

理由：SCAIは構造主義のため、文章主体は誤読と品質劣化を招く。

---

### **G4. G番号とP番号の混在**

```
❌ P0100 に標準規範を書く
❌ G0203 にプロジェクト固有情報を書く
```

理由：標準（G）とプロジェクト（P）は絶対に混在不可。

## Appendix H – 適用領域・非適用領域

### **H1. 適用領域（SCAI が強く適する領域）**

* 要求定義書
* 仕様書（Functional / Non-functional）
* 標準文書・ガイドライン
* チェックリスト
* プロセス文書
* レビュー記録
* AI生成＋検証が必要な文書

### **H2. 非適用領域（使わない方がよい領域）**

* 物語・随筆などの純創作
* 感情表現主体の文章
* 一度きりのメモ
* 構造化が不要な自由記述

### **H3. グレーゾーン（状況次第で適用可）**

* 会議議事録（構造化すれば適用可）
* アイディアスケッチ
* 部分的に構造を要する文書
